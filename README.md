# Talos on VMware / Proxmox

A bootstrapping template for a Talos Linux cluster (3 control plane + 3 workers) on VMware vSphere or Proxmox VE, with Cilium CNI and BGP load balancer integration.

## Repository Structure

```
powershell/
  Initialize-TalosConfig.ps1     # hypervisor-agnostic: generate machine configs
  Bootstrap-TalosCluster.ps1     # hypervisor-agnostic: bootstrap etcd + kubeconfig
  VMware/                        # vSphere: OVA upload, VM deploy, resize/expand
  Proxmox/                       # Proxmox VE: image prep, VM deploy
  Arc/                           # Azure Arc onboarding
  TalosHelper/                   # shared module
exampleconfigs/                  # environment templates + bgp/helm examples
```

This repo contains only the generic, reusable parts. Site-specific and sensitive files (machine configs, credentials, environment config) should be kept in a separate folder of your own choosing - outside this repo.

Every script takes a `-EnvironmentFile` parameter pointing **directly at your environment yaml file**; generated files (`talosfiles/`) are written next to it:

```powershell
.\powershell\VMware\Deploy-TalosCluster.ps1 -EnvironmentFile "C:\path\to\your\configs\environment.yaml"
```

Your configs folder ends up containing:

```
configs/
  environment.yaml        # filled in from exampleconfigs/environment.vmware.example.yaml
                          # (or environment.proxmox.example.yaml)
  talosfiles/
    controlplane.yaml     # generated by Initialize-TalosConfig.ps1
    worker.yaml           # generated by Initialize-TalosConfig.ps1
    talosconfig           # generated by Initialize-TalosConfig.ps1
    kubeconfig            # written by Bootstrap-TalosCluster.ps1
```

```yaml
customization:

      - siderolabs/vmtoolsd-guest-agent
```

- **Schematic ID:** `a28d86375cf9debe952efbcbe8e2886cf0a174b1f4dd733512600a40334977d7`

## Prerequisites

- `talosctl` installed locally
- `kubectl` installed locally
- PowerShell with `VCF.PowerCLI` and `powershell-yaml` modules installed
- A reserved VIP (Virtual IP) on your VM network for the control plane endpoint (e.g. `192.168.1.50`)
- 6 VM IP addresses planned (3 control plane, 3 workers) - DHCP or static

Copy `exampleconfigs/environment.vmware.example.yaml` to your configs folder as `environment.yaml` and fill in all values before running any scripts.

---

## Step 1 - Import OVA into content library

```powershell
.\powershell\VMware\Upload-TalosOva.ps1 -EnvironmentFile "C:\path\to\your\configs\environment.yaml"
```

This downloads the OVA from Image Factory and imports it into the content library defined in `environment.yaml` (default: `TALOS`).
Bumping the `version` in `environment.yaml` and re-running will upload the new version alongside the old one.

---

## Step 2 - Generate machine configs

Generate the base configs (per-node networking and hostname are applied at deploy time via patches):

```powershell
.\powershell\Initialize-TalosConfig.ps1 -EnvironmentFile "C:\path\to\your\configs\environment.yaml"
```

This reads the environment file and runs `talosctl gen config` with the correct cluster name, VIP endpoint, and install image. Output goes to `talosfiles/` inside your configs folder.

To regenerate (e.g. after changing schematic version):

```powershell
.\powershell\Initialize-TalosConfig.ps1 -EnvironmentFile "C:\path\to\your\configs\environment.yaml" -Force
```

---

## Step 3 - Deploy cluster VMs

```powershell
.\powershell\VMware\Deploy-TalosCluster.ps1 -EnvironmentFile "C:\path\to\your\configs\environment.yaml"
```

This creates VMs from the content library (3 control plane + 3 workers), injects the machine configs via `guestinfo.talos.config`, sets `disk.enableUUID=TRUE`, and powers them on. VM names match the hostnames defined in `environment.yaml`.

| Role          | VMs                                                     | vCPU | RAM  | Disk   |
|---------------|---------------------------------------------------------|------|------|--------|
| Control plane | `talos-cp-1`, `talos-cp-2`, `talos-cp-3`               | 2    | 4 GB | 50 GB  |
| Worker        | `talos-worker-1`, `talos-worker-2`, `talos-worker-3`   | 4    | 8 GB | 200 GB |

---

## Step 4 - Bootstrap the cluster

```powershell
.\powershell\Bootstrap-TalosCluster.ps1 -EnvironmentFile "C:\path\to\your\configs\environment.yaml"
```

The script will:
1. Read control plane IPs directly from the environment file
2. Wait for the Talos API (port 50000) to be ready on all control plane nodes
3. Bootstrap etcd on the first control plane node
4. Wait for all control plane members to join
5. Write `kubeconfig` to the configs folder

---

## Step 5 - Install Cilium CNI

Nodes will remain `NotReady` until a CNI is installed - this is expected.

```bash
helm repo add cilium https://helm.cilium.io/
helm repo update
helm install cilium cilium/cilium --namespace kube-system --values helm/cilium/values.yaml
```

Check status of Cilium pods:

```bash
cilium status --wait
```

To upgrade Cilium later:

```bash
helm upgrade cilium cilium/cilium --namespace kube-system --values helm/cilium/values.yaml
```

---

## Step 6 - Configure BGP

Copy `exampleconfigs/bgp.yaml` and fill in your values (`<LOCAL_ASN>`, `<ROUTER_ASN>`, `<ROUTER_IP>`, `<LB_CIDR>`, `<ROUTER_NAME>`), then apply it:

```bash
kubectl label nodes --all bgp-policy=default
kubectl apply -f bgp.yaml
```

Verify peering is established:

```bash
cilium bgp peers
```

---

## Step 7 - Verify the cluster

```powershell
$env:KUBECONFIG = "C:\path\to\your\configs\kubeconfig"
kubectl get nodes
```

All 6 nodes should appear `Ready` once Cilium is running.

---

## Step 8 - Install Gateway API CRDs

Gateway API CRDs are required before Traefik can act as a Gateway controller:

```bash
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/latest/download/standard-install.yaml
```

---

## Step 9 - Install ArgoCD

```bash
helm repo add argo https://argoproj.github.io/argo-helm
helm repo update
helm install argocd argo/argo-cd --namespace argocd --create-namespace --values helm/argocd/values.yaml
```

The `helm/argocd/values.yaml` configures the server service as a LoadBalancer with BGP labels, so Cilium will assign it an IP from the pool and announce it to your router.

Get the initial admin password:

```bash
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d
```

## Resizing worker disks

The worker VM's single disk holds both Talos and Longhorn's data
(`/var/lib/longhorn` lives on the EPHEMERAL partition). To give Longhorn more
space, grow the disks in place — Talos auto-expands EPHEMERAL on boot and the
Longhorn replica data is preserved.

```powershell
.\powershell\VMware\Worker-Management\Expand-TalosWorkerDisk.ps1 -EnvironmentFile "C:\path\to\your\configs\environment.yaml"
```

Processes one worker at a time: grows the VMDK to `-TargetDiskGB` (default 200),
cordons + drains, reboots via `talosctl`, waits for the node to return Ready,
then waits for all Longhorn volumes to be healthy again before moving on — so 2
healthy replicas stay available throughout. Use `-Node talos-worker-2` to do a
single node, or `-SkipDrain` to skip the eviction step. Keep `worker.diskGB` in
`environment.yaml` in sync with the target so future deploys match.

## Proxmox

The same workflow works on Proxmox VE using the scripts in `powershell/Proxmox/`.
Instead of an OVA + guestinfo, the factory **nocloud** disk image is booted directly
and the machine config is delivered as cloud-init user-data (`cicustom` snippet) —
Talos' nocloud platform reads the machine config from there.

Schematic for Proxmox (adds the QEMU guest agent):

```yaml
customization:
  systemExtensions:
    officialExtensions:
      - siderolabs/iscsi-tools
      - siderolabs/util-linux-tools
      - siderolabs/qemu-guest-agent
```

- **Schematic ID:** `88d1f7a5c4f1d3aba7df787c448c1d3d008ed29cfb34af53fa0df4336a56040b`
- **Talos version:** `v1.13.6`
- **Image:** `https://factory.talos.dev/image/<schematic-id>/<version>/nocloud-amd64.raw.xz`

Prerequisites (in addition to `talosctl`/`kubectl`/`powershell-yaml`):

- `Posh-SSH` PowerShell module (`Install-Module Posh-SSH -Scope CurrentUser`) —
  the scripts prompt once for the SSH password (root by default) and reuse the
  connection for all commands
- A storage with `snippets` content enabled (default `local`, `/var/lib/vz/snippets`)

Copy `exampleconfigs/environment.proxmox.example.yaml` to your configs folder as
`environment.yaml` and fill in the `proxmox` section. Then:

```powershell
# 1. Download the nocloud image onto each Proxmox host
.\powershell\Proxmox\Prepare-TalosImage.ps1 -EnvironmentFile "C:\path\to\your\configs\environment.yaml"

# 2. Generate machine configs (picks the plain installer image automatically)
.\powershell\Initialize-TalosConfig.ps1 -EnvironmentFile "C:\path\to\your\configs\environment.yaml"

# 3. Create and start the VMs
.\powershell\Proxmox\Deploy-TalosCluster.ps1 -EnvironmentFile "C:\path\to\your\configs\environment.yaml"

# 4. Bootstrap (hypervisor-agnostic, same script as VMware)
.\powershell\Bootstrap-TalosCluster.ps1 -EnvironmentFile "C:\path\to\your\configs\environment.yaml"
```

VMs are created per the Proxmox guide's recommendations: `q35` machine, UEFI
(`ovmf`, secure boot disabled), `host` CPU type, VirtIO SCSI controller, ballooning
disabled, QEMU guest agent enabled. The OS disk is imported from the nocloud image
(`scsi0` = `/dev/sda`), worker data disks follow as `scsi1` = `/dev/sdb`, etc. —
matching the device mapping in the generated machine configs.

Steps 5+ (Cilium, BGP, ArgoCD, ...) are identical to VMware. For upgrades use the
plain installer image: `factory.talos.dev/installer/<schematic-id>:<version>`.

## Upgrading Talos

When a new Talos version is released, generate a new schematic at [factory.talos.dev](https://factory.talos.dev) with the same extensions, then upgrade each node:

```bash
# Upgrade control plane nodes one at a time
talosctl upgrade -n <cp-1-ip> --image factory.talos.dev/installer/<new-schematic-id>:<new-version>
talosctl upgrade -n <cp-2-ip> --image factory.talos.dev/installer/<new-schematic-id>:<new-version>
talosctl upgrade -n <cp-3-ip> --image factory.talos.dev/installer/<new-schematic-id>:<new-version>

# Then worker nodes
talosctl upgrade -n <worker-1-ip> --image factory.talos.dev/installer/<new-schematic-id>:<new-version>
talosctl upgrade -n <worker-2-ip> --image factory.talos.dev/installer/<new-schematic-id>:<new-version>
talosctl upgrade -n <worker-3-ip> --image factory.talos.dev/installer/<new-schematic-id>:<new-version>
```

Talos upgrades in-place with an A/B partition scheme - each node reboots into the new version without data loss.
